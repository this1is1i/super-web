# 超级井字棋（Super Tic-Tac-Toe）

一个支持本地 AI、在线双人对战和特殊棋盘交换规则的超级井字棋网页游戏。项目使用原生 HTML、CSS 与 JavaScript 构建，Node.js 服务端同时提供静态页面和 WebSocket 房间服务，无框架、无打包步骤。

## 功能概览

- 3 种棋盘规则：普通、循环交换、混沌交换
- 3 种对手模式：在线双人、普通 AI、困难 AI
- 服务端权威判定在线落子、回合、交换与计分
- 6 位房间 ID，支持创建房间和加入房间
- 断线重连：意外断开后默认保留席位 5 分钟
- 对局前可申请交换先后手，需对方确认并带有冷却限制
- 房间内文字和图片聊天，支持 JPEG、PNG、WebP
- 响应式单屏棋盘、当前棋盘提示、最近步骤与消息预览
- 共享规则模块：浏览器、服务端与 AI 使用同一套状态转换逻辑
- 基于 Node.js 内置测试运行器的规则、AI、协议和界面约束测试

## 快速开始

### 环境要求

- Node.js
- npm
- 支持 WebSocket、Canvas 和现代 JavaScript 的浏览器

### 安装并启动

```bash
npm install
npm start
```

服务默认监听 `0.0.0.0:8080`。本地开发时会尝试自动打开浏览器；如果没有自动打开，请访问：

```text
http://localhost:8080
```

Windows 用户也可以双击 `启动游戏.bat`。脚本会检查 Node.js，在缺少 `node_modules` 时安装依赖，然后启动服务。

> 不要直接双击打开 `index.html`。页面资源使用站点根路径，在线功能也依赖同端口的 HTTP/WebSocket 服务，应通过 `npm start` 提供的地址访问。

## 游戏方式

### 本地 AI

1. 打开右上角“设置”。
2. 在“对手模式”中选择“普通人机”或“困难人机”。
3. 选择棋盘规则；特殊模式还可以设置每隔几手交换一次。
4. 点击“应用并开始新局”。

AI 对局全部在浏览器本地完成，不依赖房间服务。玩家使用 X，并且先手。

### 在线双人

1. 保持“对手模式”为“对战”。
2. 打开“设置”，确认 WebSocket 地址并连接服务器。
3. 一名玩家创建房间，将 6 位房间 ID 发给另一名玩家。
4. 另一名玩家输入房间 ID 并加入。
5. 双方进入同一局后即可开始落子和聊天。

当页面由本项目服务提供时，客户端会自动使用当前页面主机：HTTP 页面连接 `ws://`，HTTPS 页面连接 `wss://`。

## 完整规则

棋盘由 9 个 `3×3` 小棋盘组成，每个小棋盘也包含 9 个格子。

1. 对局从中央小棋盘开始，X 先手。
2. 玩家在当前小棋盘的某一格落子；该格的绝对位置决定对手下一步要进入的小棋盘。
3. 赢得一个小棋盘可获得 1 分。填满但无人获胜的小棋盘记为平局。
4. 如果目标小棋盘已经结束，路由会沿对应棋盘内容的来源链寻找仍可落子的位置；无法继续时回退到第一个可用小棋盘。
5. 所有小棋盘结束后结算，总分更高的一方获胜；同分则为平局。

界面中的橙色光晕表示当前操作棋盘。只有轮到本地玩家时，该棋盘才会获得可点击提示。

### 计分规则

| 成就 | 得分 |
| --- | ---: |
| 赢得一个小棋盘 | +1 |
| 在大棋盘上形成 3 个已赢小棋盘的三连 | +2 |
| 三个小棋盘具有至少一种共同获胜线型，但没有形成对应的物理 9 格长线 | +3 |
| 在完整盘面形成同色的物理 9 格横线、竖线或长对角线 | +4 |

同一成就同时满足共同线型和物理长线时，只计算 `+4`，不会再叠加 `+3`。彼此独立的奖励仍然可以叠加。每次成功落子以及棋盘交换后，奖励和最终胜负都会重新计算。

## 模式说明

棋盘规则与对手模式彼此独立，因此可以组合出 9 种玩法。

### 棋盘规则

| 模式 | 行为 |
| --- | --- |
| 普通 | 小棋盘位置固定，不发生交换 |
| 循环 | 每隔 N 个成功回合，按 `1↔2、2↔3、…、8↔9、9↔1` 的固定顺序交换两个小棋盘的内容 |
| 混沌 | 每隔 N 个成功回合，由服务端在在线对局中权威随机选择两个不同位置并交换内容 |

交换的是小棋盘“内容身份”，不是绝对位置编号。一次回合的原子顺序是：

1. 落子；
2. 到期时交换棋盘；
3. 在新映射中解析对手的目标绝对位置；
4. 重新计算奖励与对局结果。

已经获胜或平局的小棋盘也可能被交换。特殊模式的交换频率 `N` 可设为 1–20。

### 对手模式

| 模式 | 说明 |
| --- | --- |
| 在线对战 | 两个浏览器客户端通过房间进行实时对战，由服务端确认状态 |
| 普通 AI | 使用带随机性的局面启发式策略，优先处理即时胜负机会 |
| 困难 AI | 使用有时间和深度上限的搜索，并带有即时获胜、阻挡与安全回退策略 |

困难 AI 默认最大搜索深度为 4，单次思考时间预算约 600 ms。

## 在线对战与聊天

### 权威状态与重复请求

在线模式中，客户端点击后只显示待确认状态。只有服务端广播 `turn_applied`，该步才算成功。每个状态带有递增的 `state_version`，服务端会拒绝过期、越权或非法请求。

客户端使用 `client_move_id` 标识落子；服务端为每名玩家保留最近 256 个 ID，使重发请求不会重复落子。

### 断线重连

- 意外断开后，席位和房间默认保留 5 分钟。
- 浏览器会在当前标签页的会话存储中保存恢复信息，并尝试重新连接。
- 对手暂时离线期间，棋盘会冻结，避免双方状态继续分叉。
- 主动离开房间不会进入宽限期，而会立即释放房间。
- 服务进程重启会清空内存中的房间、会话和聊天记录。

### 聊天限制

- 文字：每条 1–500 个字符。
- 图片：JPEG、PNG 或 WebP，服务端接收上限为 512 KiB；客户端会尝试缩放和压缩较大的图片。
- 历史：每个房间最多保留最新 100 条，且总缓存不超过 10 MiB。
- 默认限流：每 10 秒最多 5 条文字、1 张图片。

## 配置

服务端读取以下环境变量：

| 变量 | 默认值 | 说明 |
| --- | ---: | --- |
| `PORT` | `8080` | HTTP 与 WebSocket 共用的监听端口 |
| `NODE_ENV` | — | 设为 `production` 时禁止本地自动打开浏览器 |
| `RECONNECT_GRACE_MS` | `300000` | 意外断线后的席位保留时间（毫秒） |
| `CHAT_RATE_WINDOW_MS` | `10000` | 聊天限流窗口（毫秒） |
| `CHAT_TEXT_RATE_MAX` | `5` | 每个窗口允许的文字消息数 |
| `CHAT_IMAGE_RATE_MAX` | `1` | 每个窗口允许的图片消息数 |
| `CHAT_DEDUPE_MAX_IDS` | `4096` | 每名玩家保留的聊天去重 ID 数量 |

示例（PowerShell，仅对当前进程会话生效）：

```powershell
$env:PORT = "3000"
npm start
```

## 项目结构

```text
.
├── index.html                 # 单页游戏界面与弹窗结构
├── css/
│   └── main.css              # 响应式单屏布局和棋盘样式
├── js/
│   ├── game-rules.js         # 服务端、客户端、AI 共用的纯规则模块
│   ├── ai-player.js          # 普通启发式与困难搜索 AI
│   ├── main.js               # 浏览器渲染、交互、连接、聊天与恢复逻辑
│   └── server.js             # HTTP 静态服务、WebSocket 房间和权威状态
├── tests/                    # 规则、AI、协议和 UI 约束测试
├── package.json              # npm 脚本和 ws 依赖
├── render.yaml               # Render Web Service 部署配置
└── 启动游戏.bat             # Windows 快速启动脚本
```

## 技术架构

```text
浏览器 A ─┐
          ├── HTTP + WebSocket ── Node.js 服务端 ── 内存房间/会话
浏览器 B ─┘                          │
                                    └── game-rules.js

本地 AI：main.js ── ai-player.js ── game-rules.js
```

- `game-rules.js` 采用 UMD 风格，既可在浏览器中挂载，也可被 Node.js `require`。
- `server.js` 是在线对局的唯一权威状态源，负责成员身份、回合、版本、交换、聊天和重连。
- `main.js` 负责渲染与用户交互，不在在线模式中自行确认落子成功。
- `ai-player.js` 只通过共享规则模块模拟回合，避免出现与真实对局不同的规则副本。

## 部署

仓库提供 `render.yaml`，可部署为 Render Web Service：

```yaml
buildCommand: npm install
startCommand: npm start
```

其他 Node.js 托管平台也可以使用相同命令。部署时需要满足：

- 平台允许 WebSocket 长连接。
- HTTP 与 WebSocket 请求被转发到同一个 `PORT`。
- HTTPS 页面对应使用 `wss://`。
- 单实例最符合当前内存房间模型；多实例部署需要引入共享房间状态和连接路由，当前代码没有实现跨实例同步。
- 进程重启、重新部署或实例休眠会终止现有房间。

## 协议摘要

客户端发送的主要消息：

- `create_room`、`join_room`、`leave_room`
- `make_move`
- `chat_send`
- `resume_session`、`confirm_resume`
- `request_swap`、`respond_swap`
- `reset_game`

服务端返回的主要消息：

- `room_created`、`game_start`
- `turn_applied`
- `chat_message`、`chat_error`
- `session_resumed`、`resume_confirmed`、`session_error`
- `player_temporarily_disconnected`、`player_reconnected`、`player_disconnected`
- 先后手交换相关事件
- `game_reset`、`error`

`turn_applied` 是在线落子成功的唯一事件，包含服务端选定的完整回合（混沌交换对也在其中）、结果和递增后的状态版本。

## 开发约束

最重要的约束是：所有游戏状态转换必须继续复用 `js/game-rules.js`。

新增规则或修改计分时，应同时确认：

1. 服务端通过共享规则验证并应用回合；
2. 本地 AI 通过共享规则进行模拟；
3. 浏览器本地模式通过共享规则推进状态；
4. 对应测试覆盖普通模式、特殊模式及交换后的边界情况。

不要在 `server.js`、`main.js` 或 `ai-player.js` 中复制一套落子、交换、路由或计分逻辑。
